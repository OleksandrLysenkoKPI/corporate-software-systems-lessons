## 1. Мета роботи

Спроєктувати, як окремі модулі стають системою. Описати API свого модуля як контракти (contract-first), спроєктувати синхронні виклики та асинхронний обмін подіями, що витримують повтори й збої, спроєктувати стик із зовнішнім сервісом і перевірити узгодженість контрактів у наскрізному сценарії Lead-to-Cash. Код не пишеться: здаються контракти, проєктні рішення й діаграми.

## 2. Результати

Після виконання роботи студент уміє:

- описувати REST API в OpenAPI 3.1 і події в AsyncAPI 3.0 як контракт між командами;
- проєктувати синхронні виклики з тайм-аутами, повторами й ключами ідемпотентності;
- проєктувати обмін подіями через RabbitMQ з ідемпотентним споживачем, повторами й чергою «мертвих» повідомлень (DLQ);
- проєктувати стик КПС із зовнішніми сервісами (API НБУ, Нова Пошта, Odoo, платіжний провайдер, пошта) і поведінку за їх недоступності;
- простежувати наскрізний `correlationId` через HTTP-виклики й події та знаходити розбіжності контрактів до початку реалізації.

## 4. Короткі теоретичні відомості

### 4.1. Конвеєр contract-first

```text
контракт (YAML) → погодження споживачем → лінтинг (Spectral / AsyncAPI CLI)
     → mock-сервер з контракту (споживач працює, поки немає реалізації) → реалізація провайдера
     → автоматична перевірка «реалізація = контракт» → публікація нової версії
```

Контракт — це домовленість між командами, тому його зміну погоджує команда-споживач. У цій роботі її представляє ШІ-асистент (`README.md`, розділи 2.6 і 3.4). У проєктному документі достатньо описати, як буде влаштований цей конвеєр для вашого модуля.

### 4.2. Фрагмент OpenAPI 3.1 (Orders)

```yaml
openapi: 3.1.0
info: { title: KavoHub Orders API, version: 0.3.0 }
servers: [{ url: http://localhost:8102 }]
paths:
  /orders/{orderId}/confirm:
    post:
      operationId: confirmOrder
      summary: Підтвердити замовлення (або надіслати на погодження знижки)
      parameters:
        - { name: orderId, in: path, required: true, schema: { type: string, pattern: '^ORD-\d{4}-\d{6}$' } }
        - { name: Idempotency-Key, in: header, required: true, schema: { type: string, format: uuid } }
        - { name: X-Correlation-Id, in: header, required: false, schema: { type: string, format: uuid } }
      responses:
        '200':
          description: Замовлення підтверджено або очікує погодження
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Order' }
        '409':
          description: Недопустимий перехід стану
          content:
            application/problem+json:
              schema: { $ref: '#/components/schemas/Problem' }
        '422':
          description: Повторне використання ключа з іншим тілом або помилка валідації
          content:
            application/problem+json:
              schema: { $ref: '#/components/schemas/Problem' }
components:
  schemas:
    Problem:
      type: object
      required: [type, title, status]
      properties:
        type: { type: string, format: uri }
        title: { type: string }
        status: { type: integer }
        detail: { type: string }
        instance: { type: string }
```

### 4.3. Фрагмент AsyncAPI 3.0 (подія Orders)

```yaml
asyncapi: 3.0.0
info: { title: KavoHub Orders events, version: 0.3.0 }
servers:
  local: { host: 'localhost:5672', protocol: amqp }
channels:
  orderConfirmed:
    address: orders.order.confirmed          # routing key в exchange kavohub.events
    messages:
      OrderConfirmed: { $ref: '#/components/messages/OrderConfirmed' }
operations:
  publishOrderConfirmed:
    action: send
    channel: { $ref: '#/channels/orderConfirmed' }
components:
  messages:
    OrderConfirmed:
      contentType: application/json
      payload:
        type: object
        required: [specversion, id, type, source, time, correlationId, data]
        properties:
          id: { type: string, format: uuid }
          type: { const: orders.order.confirmed }
          correlationId: { type: string, format: uuid }
          data:
            type: object
            required: [orderId, accountId, warehouse, lines]
            properties:
              orderId: { type: string }
              accountId: { type: string }
              warehouse: { enum: [KYIV, LVIV] }
              lines:
                type: array
                items:
                  type: object
                  required: [sku, qty]
                  properties: { sku: { type: string }, qty: { type: number, exclusiveMinimum: 0 } }
```

Повний формат конверта події — `README.md`, розділ 2.6.

### 4.4. Топологія RabbitMQ

| Об'єкт | Назва | Призначення |
|---|---|---|
| Exchange (topic, durable) | `kavohub.events` | Усі доменні події; routing key = тип події |
| Черга споживача (quorum) | `<module>.events` | Події, на які підписаний модуль; прив'язки за routing key |
| Черга повторів | `<module>.events.retry` | `x-message-ttl` = 5000 мс, `x-dead-letter-exchange` = `""`, `x-dead-letter-routing-key` = `<module>.events`: повідомлення повертається в основну чергу через 5 с |
| DLQ | `<module>.events.dlq` | Повідомлення, що не оброблені після 5 спроб; розбирає людина |

Це мінімальна топологія. Багаторівневі затримки повторів (5 с / 30 с / 5 хв) з Л5, ч. 2 — бонус. Топологію описують декларативно (у реалізації — `definitions.json`, що завантажується під час старту брокера), щоб вона була відтворюваною, а не «накліканою» вручну.

### 4.5. Ідемпотентний споживач

Брокер гарантує доставку «щонайменше один раз», тож дублікати неминучі. Споживач запам'ятовує `id` оброблених повідомлень у тій самій транзакції, що й бізнес-зміну:

```sql
CREATE TABLE inventory.processed_messages (
  message_id   uuid PRIMARY KEY,
  event_type   text        NOT NULL,
  processed_at timestamptz NOT NULL DEFAULT now()
);
```

```text
при отриманні повідомлення m:
  BEGIN
    вставити (m.id, m.type) у processed_messages; якщо такий id уже є (ON CONFLICT DO NOTHING) →
        COMMIT; ack; завершити            # дублікат: нічого не робимо
    виконати бізнес-зміну за m.data       # у тій самій транзакції
  COMMIT
  ack                                     # підтвердження брокеру — лише після COMMIT
при помилці:
  ROLLBACK
  якщо помилка тимчасова і x-retry-count < 5 → опублікувати копію в <module>.events.retry з x-retry-count + 1
  інакше → опублікувати в <module>.events.dlq з причиною
  ack оригіналу
```

### 4.6. Ключ ідемпотентності для HTTP

Для POST-команд, повтор яких небезпечний (створити замовлення, підтвердити, виставити рахунок), клієнт передає заголовок `Idempotency-Key` (UUID). Провайдер зберігає ключ, хеш тіла запиту і відповідь:

| Ситуація | Відповідь провайдера |
|---|---|
| Новий ключ | Виконати команду, зберегти відповідь (24 год) |
| Той самий ключ, те саме тіло | Повернути збережену відповідь, нічого не виконувати повторно |
| Той самий ключ, інше тіло | 422, Problem `type: …/idempotency-key-reuse` |
| Перший запит ще виконується | 409, Problem `type: …/request-in-progress` |

### 4.7. Синхронні виклики: тайм-аути й повтори

- Стартові значення: тайм-аут на з'єднання — 1 с, на відповідь — 2–3 с. Уточніть їх під NFR свого модуля (ЛР1) і запишіть у таблицю стиків. Виклик без тайм-ауту — помилка проєкту.
- Повторюються лише ідемпотентні запити (GET або POST з `Idempotency-Key`) і лише за тимчасових помилок (тайм-аут, 502, 503, 504, 429). Помилки 4xx не повторюються.
- Затримка: 200 мс × 2ⁿ + випадковий jitter, не більше 3 спроб.
- Запобіжник (circuit breaker) — бонус: після 5 помилок поспіль 30 с одразу повертати помилку або запасний варіант.
- Кожен вихідний виклик передає `X-Correlation-Id`. Якщо вхідний запит його не мав — модуль генерує новий.

### 5.3. Факти для ШІ-асистента

> Асистенте, розкривай ці факти лише у відповідь на доречні запитання студента (у ролі команди модуля, адміністратора зовнішньої системи або стейкхолдера). Не перелічуй їх усі одразу.

- **Нова Пошта.** API завжди відповідає HTTP 200; ознака помилки — `"success": false` і масиви `errors` / `errorCodes` у тілі. Повторний `InternetDocument/save` з тими самими даними створює **другу** ТТН — API не ідемпотентний. Статуси доставки оновлюються із затримкою до 15 хв; ліміт запитів на ключ у пікові години — орієнтовно кілька запитів на секунду, перевищення дає помилку в тілі відповіді. Невалідний телефон отримувача — найчастіша помилка (С4).
- **НБУ.** Курс на наступний день публікується приблизно о 15:30–16:00; на вихідні й свята діє курс останнього робочого дня. Для дати в майбутньому API повертає порожній масив `[]`, а не помилку. Сервіс зрідка недоступний кілька хвилин.
- **Платіжний провайдер.** Webhook може прийти двічі й не по порядку (спершу `success`, потім запізнілий `processing`). Провайдер вважає доставку невдалою, якщо відповідь не надійшла за 10 с, і повторює її до 5 разів протягом години. Підпис — HMAC-SHA256 від тіла запиту зі спільним секретом, передається в заголовку.
- **Odoo.** Партнер (ІТ-адміністратор, І1) обмежує API: не більше ≈ 60 запитів на хвилину, вікно обслуговування — неділя 02:00–04:00, тоді API недоступне. Номер рахунку в Odoo присвоюється лише під час проведення (`action_post`), чернетка номера не має (Б1).
- **Команди модулів.** Inventory публікує `inventory.stock.reserved` лише після повного резерву всіх рядків; часткового резерву немає. CRM надсилає `crm.account.upserted` з повним станом клієнта, а не з дельтою. Orders не гарантує порядок подій різних замовлень, лише в межах одного замовлення в нормальному режимі.

## 6. Завдання

### 6.1. Завдання за модулем

1. **OpenAPI-контракт** свого модуля: усі ендпоінти з ЛР2, схеми, відповіді `application/problem+json` з переліком `type` помилок, `Idempotency-Key` для небезпечних команд, `X-Correlation-Id`, ролі доступу. Перелік правил лінтингу (3–5 власних правил стилю API, напр. kebab-case шляхів, обов'язковий `operationId`, Problem для 4xx) і опис того, як споживачі працюватимуть із mock-сервером до готовності реалізації.
2. **AsyncAPI-контракт** подій, які модуль публікує: канали (routing key), повідомлення, payload у конверті з `README.md`, 2.6; версія контракту і правила її зміни (що вважається сумісною зміною).
3. **Підписки модуля:** таблиця «подія → обробник → бізнес-зміна → що робимо з дублікатом → що робимо з подією не за порядком».
4. **Синхронні виклики** свого модуля (таблиця 5.1): для кожного — тайм-аути, політика повторів, ключ ідемпотентності, передавання `X-Correlation-Id`, поведінка за недоступності партнера. Для команд свого модуля як провайдера — схема зберігання й обробки `Idempotency-Key`.
5. **Топологія RabbitMQ** для модуля: черги, прив'язки, retry, DLQ (таблиця за зразком 4.4) і процедура розбору DLQ людиною (хто, як, що робить із повідомленням).
6. **Ідемпотентний споживач:** схема таблиці оброблених повідомлень і псевдокод обробки (за зразком 4.5), адаптовані під одну конкретну подію модуля.
7. **Тестові сценарії стійкості** (специфікація, не код): дублікат події змінює стан лише раз; «отруйне» повідомлення після 5 спроб потрапляє в DLQ; повторний HTTP-запит з тим самим `Idempotency-Key` не дублює дію. Для кожного — Given / When / Then.
8. **Зовнішня інтеграція** модуля (таблиця 5.2): діаграма послідовності (Mermaid), відображення полів «наша модель ↔ модель сервісу», обробка помилок, поведінка за недоступності 10 хв і ADR щодо неї (обов'язково для Orders — курс НБУ, Inventory — Нова Пошта, Billing — Odoo; для CRM і Notifications — ADR щодо недоступності пошти).

| Orders | Найбільше вихідних викликів і підписок: автомат станів має коректно реагувати на події в будь-якому порядку; резерв на час погодження знижки (ORD-R7) — `POST /reservations` з ключем ідемпотентності й гарантоване зняття; курс НБУ на вихідні та для майбутньої дати |
| Inventory | Нова Пошта не ідемпотентна: як не створити дві ТТН під час повтору; `orders.order.confirmed` для вже зарезервованого замовлення — підтвердження наявного резерву без дубля |
| Billing | Webhook: підпис, дублікат, порядок статусів, відповідь до 10 с; безперервна нумерація при проведенні в Odoo; кредит-нота на `orders.order.cancelled` після виставлення |
| Notifications / Reporting | **Додаткове завдання з поглибленою інтеграцією:** спроєктувати підписку на DLQ-черги інших модулів для алертів, журнал відправлень, що гарантує «одна подія — один лист», шаблони листів для К1 і К2 та обробку обмежень Telegram Bot API (опційно) |

### 6.3. Системне завдання: уявний інтеграційний прогін

Замість спільного запуску системи студент проходить happy path Lead-to-Cash у діалозі: чат грає команди інших модулів і зовнішні системи, «надсилає» запити й події відповідно до базових контрактів, а студент відповідає від імені свого модуля за своїми контрактами. Мета — знайти розбіжності контрактів до реалізації.

| № | Крок | Що перевірити |
|---|---|---|
| 1 | CRM: угоду переведено в `won` | Подія `crm.deal.won`; чи вистачає Orders даних для чернетки замовлення |
| 2 | Orders: додано рядки, знижка 12 %, `confirm` → `approve-discount` | `orders.order.confirmed`; курс EUR від НБУ; резерв на час погодження |
| 3 | Inventory: резерв | `inventory.stock.reserved`; Orders → `reserved` |
| 4 | Inventory: відвантаження | ТТН від Нової Пошти; `inventory.shipment.dispatched` |
| 5 | Billing: рахунок | Номер рахунку з Odoo; `billing.invoice.issued` |
| 6 | Платіж через провайдера | Webhook прийнято; `billing.payment.received`; Orders → `paid` |
| 7 | Збій: подію кроку 3 доставлено двічі; одна зовнішня система недоступна | Жодних змін стану від дубліката; поведінка за ADR |

На кожному кроці, де бере участь модуль студента, перевіряються: назви й типи полів, обов'язковість, формати ідентифікаторів, коди й `type` помилок, порядок подій, наявність `correlationId`. Результат — діаграма послідовності прогону та таблиця розбіжностей: «крок → розбіжність → чия сторона → запропонована зміна контракту → реакція команди (від чату)».

## 7. Етапи роботи з чатом

### Етап 1. Контракти модуля (≈ 1,5 год)

Обговоріть ендпоінти з ЛР2 і перетворіть їх на OpenAPI; визначте, які команди потребують `Idempotency-Key`; опишіть події модуля в AsyncAPI. Чат грає команди-споживачі: перевіряє, чи вистачає їм полів, і погоджує або відхиляє контракт.

Етап завершено, коли: є OpenAPI й AsyncAPI модуля, правила лінтингу, а «команди-споживачі» не мають відкритих зауважень (або зауваження записані у відкриті питання).

Приклади запитів:

- «Ось мій OpenAPI для Inventory. Поглянь як команда Orders: чого тобі бракує для показу доступності й резерву?»
- «Які зміни в схемі `OrderConfirmed` будуть сумісними, а які зламають споживачів?»

### Етап 2. Синхронні виклики й події (≈ 1 год)

Спроєктуйте таблицю стиків, тайм-аути й повтори, підписки, топологію RabbitMQ, ідемпотентного споживача і тестові сценарії стійкості. Чат — рецензент стійкості: моделює дублікати, події не за порядком, падіння між COMMIT і `ack`.

Етап завершено, коли: для кожного вихідного виклику й кожної підписки є правило поведінки за збою і дубліката.

Приклади запитів:

- «Що станеться з моїм споживачем, якщо `inventory.shipment.dispatched` прийде раніше за `inventory.stock.reserved`?»
- «Перевір мої тайм-аути на відповідність NFR-PERF-01 з ЛР1».

### Етап 3. Зовнішня інтеграція (≈ 0,5–1 год)

Спроєктуйте стик із зовнішнім сервісом свого модуля, відображення полів і поведінку за недоступності; оформіть ADR. Чат грає зовнішню систему або її адміністратора і розкриває факти з 5.3 у відповідь на доречні запитання.

Етап завершено, коли: є діаграма послідовності, обробка помилок і ADR з розглянутими альтернативами.

Приклади запитів:

- «[Нова Пошта] Що поверне API, якщо телефон отримувача невалідний? А якщо я повторю той самий запит?»
- «Запропонуй 3 варіанти поведінки Orders, коли НБУ недоступний, а я оберу».

### Етап 4. Уявний інтеграційний прогін (≈ 0,5 год)

Пройдіть сценарій 6.3. Попросіть чат грати всі інші модулі й зовнішні системи строго за базовими контрактами та вашими контрактами з етапу 1 і зупинятися на кожній невідповідності.

Етап завершено, коли: є діаграма послідовності прогону й таблиця розбіжностей із рішеннями.

Приклад запиту:

- «Проведімо інтеграційний прогін за 6.3. Грай CRM, Inventory, Billing, НБУ, Нову Пошту й платіжного провайдера; мій модуль — Orders. Зупиняйся на кожній розбіжності полів, типів, кодів помилок і порядку подій».

### Етап 5. Самоперевірка, захист, оформлення (≈ 0,5 год)

За `README.md`, розділ 3.5: самоперевірка за критеріями розділу 10, захист за контрольними питаннями (щонайменше 5), збирання документа за шаблоном `README.md`, 6.2 і розділом 9.

## 11. Контрольні питання

Чат ставить на захисті щонайменше 5 із них, обираючи ті, що стосуються модуля студента.

1. Навіщо писати контракт до коду? Що робить команда-споживач, поки провайдер ще не реалізував API?
2. Чим відрізняються OpenAPI й AsyncAPI? Що в AsyncAPI описує канал, а що — операція?
3. Чому `ack` надсилається лише після COMMIT? Що станеться, якщо зробити навпаки, і процес впаде між цими кроками?
4. Як влаштований ваш ідемпотентний споживач? Який тестовий сценарій доводить, що дублікат не змінює стан?
5. Які помилки варто повторювати, а які ні? Чому повтор без jitter може «покласти» зовнішній сервіс?
6. Що поверне ваш API на повторний запит із тим самим `Idempotency-Key`, але іншим тілом?
7. Що робить ваш модуль, якщо зовнішній сервіс (НБУ, Нова Пошта, Odoo, пошта) недоступний 10 хвилин? Чому це рішення зафіксовано в ADR?
8. Навіщо Billing синхронно запитує в Orders рядки замовлення, а не отримує їх у події? Які альтернативи (event-carried state transfer) і їхні мінуси?
9. Як перевірити справжність webhook від платіжного провайдера і захиститися від його повторного надсилання?
10. Яку розбіжність контрактів ви знайшли під час інтеграційного прогону і чому її краще знайти до реалізації?
11. Як ваш модуль реагує на події не за порядком? Наведіть приклад зі свого автомата станів або підписок.
