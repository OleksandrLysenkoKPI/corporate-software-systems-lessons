## 4. Короткі теоретичні відомості

### 4.1. Проблема подвійного запису і transactional outbox

У проєкті ЛР3 модуль змінює БД і публікує подію двома окремими діями. Якщо процес упаде між ними, БД і події розійдуться: замовлення підтверджене, а склад про це не дізнається. Transactional outbox розв'язує це так: подія записується в таблицю `outbox` у **тій самій транзакції**, що й бізнес-зміна, а окремий процес-ретранслятор (relay) публікує записи з `outbox` у брокер.

```sql
CREATE TABLE orders.outbox (
  id            uuid        PRIMARY KEY,          -- = id події в конверті
  event_type    text        NOT NULL,             -- orders.order.confirmed
  aggregate_id  text        NOT NULL,             -- ORD-2026-004213
  payload       jsonb       NOT NULL,             -- повний конверт події
  created_at    timestamptz NOT NULL DEFAULT now(),
  published_at  timestamptz                       -- NULL = ще не опубліковано
);
CREATE INDEX outbox_unpublished ON orders.outbox (created_at) WHERE published_at IS NULL;
```

```text
ретранслятор (кожні 500 мс):
  BEGIN
    вибрати до 100 записів WHERE published_at IS NULL ORDER BY created_at
      FOR UPDATE SKIP LOCKED                 # кілька екземплярів не публікують одне й те саме
    для кожного: опублікувати в kavohub.events (з publisher confirms) → published_at = now()
  COMMIT
```

Ретранслятор може опублікувати подію двічі: опублікував, а COMMIT не встиг. Тому ідемпотентний споживач із ЛР3 залишається обов'язковим. Outbox гарантує «щонайменше один раз», а «рівно один раз за ефектом» дає пара «outbox + ідемпотентний споживач».

### 4.2. Сага виконання замовлення

Виконання замовлення — довга бізнес-транзакція через кілька модулів. Розподіленої ACID-транзакції між ними немає. Тому кожен крок — локальна транзакція, а для відміни виконаних кроків передбачено компенсаційні дії.

| Крок | Модуль | Дія | Компенсація |
|---|---|---|---|
| 1 | Orders | Підтвердити замовлення | Скасувати замовлення |
| 2 | Inventory | Зарезервувати товар | Зняти резерв |
| 3 | Inventory | Відвантажити, створити ТТН | — (точка неповернення: далі лише повернення товару) |
| 4 | Billing | Виставити рахунок, передати в Odoo | Кредит-нота |
| 5 | Billing | Зарахувати оплату | — |

Базовий варіант курсу, описаний у лекціях, — **оркестрація**: Orders тримає стан саги й керує кроками. Можна обрати **хореографію** (модулі реагують на події одне одного, як у ЛР3), якщо обґрунтувати це в ADR. Для навчальної системи прийнятні обидва варіанти.

### 4.3. Аудит змін

```sql
CREATE TABLE billing.audit_log (
  id              bigserial   PRIMARY KEY,
  entity          text        NOT NULL,      -- 'invoice'
  entity_id       text        NOT NULL,      -- 'КХ-2026-000123'
  action          text        NOT NULL,      -- 'issued', 'payment_allocated', 'credit_note_created'
  changed_by      text        NOT NULL,      -- користувач або svc-* (з токена, ЛР6)
  correlation_id  uuid,
  old_value       jsonb,
  new_value       jsonb,
  changed_at      timestamptz NOT NULL DEFAULT now()
);
```

Журнал аудиту лише доповнюється: обліковий запис модуля в БД має права `INSERT` і `SELECT`, але не `UPDATE` і `DELETE` на цю таблицю.

### 4.4. Міграція даних зі старої системи

```text
профілювання → правила очищення і мапінгу → пробний прогін (dry run) → імпорт з валідацією
     → звіт (прийнято / виправлено / відхилено з причиною) → звірка з джерелом → повторний запуск без дублікатів
```

- **Профілювання:** кількість рядків, порожні значення, унікальність ключів, формати, кодування, викиди.
- **Правила** записуються таблицею (поле джерела → поле цілі, перетворення, що робимо з поганим значенням) і погоджуються із «власником даних» — роль грає чат (наприклад, Наталія Шевчук для рахунків, Андрій Бондар для клієнтів).
- **Ідемпотентність:** повторний запуск того самого файлу не створює дублікатів (upsert за природним ключем: ЄДРПОУ, SKU, номер рахунку).
- **Звірка:** кількості й контрольні суми в джерелі та цілі збігаються з урахуванням відхилених рядків.

### 4.5. Дані для BI

BI-інструмент не повинен читати внутрішні таблиці модулів: вони змінюються з кожним релізом. Кожен модуль публікує **звітні представлення** (views) у схемі `reporting_<module>` — стабільний контракт для аналітики. Metabase підключається окремою роллю лише з правом `SELECT` на ці представлення.

```sql
CREATE ROLE bi_reader LOGIN PASSWORD :'bi_password';
CREATE SCHEMA reporting_billing;
CREATE VIEW reporting_billing.receivables_aging AS
SELECT i.account_id,
       sum(i.total_with_vat - i.paid_amount) FILTER (WHERE current_date - i.due_date BETWEEN 1 AND 30)  AS overdue_1_30,
       sum(i.total_with_vat - i.paid_amount) FILTER (WHERE current_date - i.due_date BETWEEN 31 AND 60) AS overdue_31_60,
       sum(i.total_with_vat - i.paid_amount) FILTER (WHERE current_date - i.due_date > 60)              AS overdue_61_plus
FROM billing.invoices i
WHERE i.status IN ('issued', 'partially_paid')
GROUP BY i.account_id;
GRANT USAGE ON SCHEMA reporting_billing TO bi_reader;
GRANT SELECT ON ALL TABLES IN SCHEMA reporting_billing TO bi_reader;
```

Метрику визначають однозначно: назва, бізнес-питання, формула, джерело (представлення), зріз, частота оновлення, власник. «Середній чек» без уточнення «з ПДВ чи без, лише відвантажені чи всі підтверджені» — не визначення.

### 4.6. Резервне копіювання: RPO і RTO

- **RPO** (Recovery Point Objective) — скільки даних допустимо втратити. Наприклад, щоденний бекап означає RPO до 24 год.
- **RTO** (Recovery Time Objective) — за скільки часу система має відновитися.
- Цілі задає бізнес у NFR (ЛР1). Бекап, відновлення з якого жодного разу не перевіряли, вважається відсутнім (кейс GitLab, Л7).

```bash
# резервна копія однієї схеми у форматі custom (стиснений, з можливістю вибіркового відновлення)
pg_dump --format=custom --schema=billing --file=/backups/billing-$(date +%F-%H%M).dump "$DATABASE_URL"
# відновлення в окрему БД для перевірки
createdb kavohub_restore_check
pg_restore --dbname=kavohub_restore_check --no-owner /backups/billing-2026-12-01-0300.dump
```

Команди наведено як ілюстрацію для runbook — виконувати їх у цій роботі не потрібно.

### 5.3. Факти для ШІ-асистента

> Асистенте, розкривай ці факти лише у відповідь на доречні запитання студента (профілювання, запитання до власника даних). Не видавай їх списком.

1. **Outbox.** Таблиця `outbox` модуля, перелік подій, що через неї проходять, проєкт ретранслятора (частота, розмір пачки, publisher confirms, що робити з «отруйним» записом, очищення опублікованих).
2. **Сага.** Своя частина саги: які команди й події модуль приймає й видає, стани (з урахуванням ЛР2), компенсації, тайм-аути. Сценарії збою з таблиці 5.1 для свого модуля + щонайменше 2 власні.
3. **Проєкт сценаріїв збою.** Для кожного сценарію — тест-специфікація (6.3).
4. **Аудит.** Журнал аудиту ключової сутності модуля: які дії аудитуються, структура запису, права, `correlationId`, строк зберігання.
5. **Міграція.** Для свого файлу (5.2): профіль даних, таблиця правил очищення й мапінгу, правила дедуплікації, план прогонів (dry run → імпорт → повторний запуск), формат звіту імпорту, план звірки, публікація подій `*.upserted` після імпорту і як споживачі витримають сотні подій поспіль.
6. **Аналітика.** Звітні представлення модуля в `reporting_<module>` (структура полів або SQL-ескіз), 2–3 метрики з визначеннями (4.5) і макет дашборду.
7. **Відновлення модуля.** Runbook відновлення схеми модуля з бекапу: кроки, хто виконує, як перевіряємо результат, що робити з outbox і споживачами після «повернення в минуле».

| Модуль | Файл міграції | Звіти (6.2, п. 6) | Акцент |
|---|---|---|---|
| CRM | `customers_legacy.xlsx` | Воронка за стадіями; конверсія лідів у виграні угоди за менеджерами (П3); список «ризик оренди» (Д3) | Дедуплікація клієнтів і вибір головного запису; порядок подій для `lastOrderAt` |
| Orders | `price_agreements.xlsx` | Замовлення за днями; середній чек; **час від підтвердження до відвантаження** і частка замовлень, відвантажених у межах доби (Д2) | Стан саги, тайм-аути, повторне підтвердження після `on_hold` |
| Inventory | `products_legacy.csv`, `stock_opening.csv` | Товари нижче мінімального запасу; залишки за категоріями і складами; прострочені резерви | Ідемпотентність резерву за `orderId`; спливання резерву |

## 7. Етапи роботи з чатом

### Етап 1. Outbox і сага

- **Що обговорити:** які зміни модуля супроводжуються подіями; де саме може статися подвійний запис; оркестрація чи хореографія; стани модуля в сазі й компенсації.
- **Ролі чату:** наставник; команди інших модулів (особливо Orders як можливий оркестратор); рецензент-архітектор.
- **Етап завершено, коли** є таблиця outbox, проєкт ретранслятора, ADR про координацію саги й діаграма саги з компенсаціями.
- **Приклади запитів:** «Ось моя таблиця outbox і алгоритм ретранслятора — знайди, де подія може загубитися або продублюватися». «Зіграй команду Orders: я пропоную хореографію, переконай мене або погодься».

### Етап 2. Сценарії збою й аудит

- **Що обговорити:** сценарії з 5.1 для свого модуля, власні сценарії, інваріанти, тест-специфікації (6.3), журнал аудиту.
- **Ролі чату:** рецензент, що «ламає» систему: дублікати, зміна порядку подій, падіння між записом у БД і публікацією, падіння споживача після обробки, але до ack, недоступність зовнішньої системи, два екземпляри ретранслятора.
- **Етап завершено, коли** кожен сценарій має очікувану поведінку, інваріант і тест-специфікацію, а чат-рецензент не знаходить сценарію, у якому дані розходяться без способу це виявити.
- **Приклади запитів:** «Атакуй мою сагу: вигадай 3 збої, які я не врахував». «Чи перевіряє моя тест-специфікація саме інваріант, а не лише "сервіс відповів 200"?»

### Етап 3. Міграція даних

- **Що обговорити:** профілювання свого файлу (запитання до чату про дані), правила очищення й мапінгу, дедуплікацію, погодження правил із власником даних, план прогонів і звірки, персональні дані.
- **Ролі чату:** «джерело даних», яке відповідає на запитання профілювання; власник даних (Бондар, Ткаченко, Шевчук), який погоджує або відхиляє правила; ІТ-адміністратор.
- **Етап завершено, коли** є профіль, таблиця правил із позначкою «погоджено / власник», план прогонів, формат звіту й план звірки.
- **Приклади запитів:** «Я профілюю `open_invoices.csv`: скільки рядків, які формати дат і номерів зустрічаються?» «[до Наталії Шевчук] Пропоную рахунки з датою у форматі мм/дд/рррр відхиляти — погоджуєте?»

### Етап 4. Аналітика й резервне копіювання

- **Що обговорити:** бізнес-питання стейкхолдерів (Д1, Д2, Д3, П3, Б2, Б5), звітні представлення, визначення метрик, макет дашборду; RPO/RTO, план бекапу, runbook відновлення свого модуля.
- **Ролі чату:** директорка й інші стейкхолдери як споживачі звітів; ІТ-адміністратор (І1: «бекапи є… здається»); рецензент з експлуатації.
- **Етап завершено, коли** кожна метрика має однозначне визначення, а runbook відповідає на питання «як ми дізнаємося, що відновлення вдалося, і що буде з подіями після відновлення».
- **Приклади запитів:** «[до директорки] Що для вас означає "відвантажили сьогодні" — за датою ТТН чи за датою передачі кур'єру?» «Перевір мій runbook: чи вкладемося ми в RTO і що я забув?»

### Етап 5. Самоперевірка, захист і оформлення

Попросіть чат провести самоперевірку за критеріями (розділ 10), захист за контрольними питаннями (розділ 11) і допомогти зібрати документ за шаблоном README, розділ 6.2, і розділом 9 цієї роботи (README, розділ 3.5).

## 11. Контрольні питання

Чат ставить щонайменше 5 питань, обираючи ті, що стосуються модуля студента.

1. Яку проблему розв'язує transactional outbox? Чому після його впровадження ідемпотентний споживач однаково потрібен?
2. Навіщо в ретрансляторі `FOR UPDATE SKIP LOCKED`? Що станеться без нього, якщо запустити два екземпляри?
3. Яку координацію саги ви обрали і чому? Що стане складнішим, якщо кроків буде не п'ять, а п'ятнадцять?
4. Чому відвантаження — точка неповернення саги? Як компенсувати кроки після неї?
5. Як ваш модуль поводиться, якщо події приходять не в тому порядку, у якому їх опублікували?
6. Який збій, запропонований чатом-рецензентом, змусив вас змінити проєкт і як саме?
7. Які дефекти ви знайшли в даних старої системи, яких не було в переліку? Як вирішили, що з ними робити, і хто це погодив?
8. Як ваш план доводить, що повторний запуск імпорту не створює дублікатів і що нічого не загубилося?
9. Чому Metabase читає звітні представлення, а не таблиці модулів? Що станеться зі звітами після наступного релізу, якщо зробити інакше?
10. Які RPO і RTO у «КавоХаб» і за рахунок чого ваш runbook у них вкладається? Що буде з подіями, якщо відновити схему на стан шестигодинної давності?
